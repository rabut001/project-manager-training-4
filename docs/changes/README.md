# 変更案件

アプリやデータを変えるときの管理資料を、案件ごとのフォルダに置く。参照元（システムアーキテクト試験の演習）の `specs/` に当たる。サイトには載せない。

## いつ作るか

画面、操作、保存、問題データ、公開のしかたを変える依頼を受けたら、実装に入る前に案件フォルダを作る。利用者から文書の作成を指示されなくても作る。質問への回答や、仕様を変えない調査だけのときは作らない。

## フォルダ

- 名前は `NNNN-短い英語の名前` とする。`NNNN` は、すでにある番号の最大に 1 を足した4桁である。
- 中身は `README.md` と、必要なら確認用の `checklist.json`（データ作業なら `checklist/<id>.json`）である。
- レビューで出た直しは、その案件のフォルダで扱う。完了した案件への別の依頼は、新しい番号のフォルダにする。
- 案件が `完了` になったあとは、そのフォルダを直さない。
- 案件フォルダは、現在の仕様の参照先にしない。現在の仕様は `docs/spec.md`、データの作り方は `docs/content-guide.md` が正本である。恒久的に使う手順は、案件フォルダではなく `docs/` 直下に書く。

## 状態

状態は、案件の `README.md` の先頭の `status:` に書く。ほかの場所には書かない。

| 状態 | 意味 |
| --- | --- |
| `文書作成` | 文書を書いていて、実装には入っていない |
| `着手` | 実装に入っている |
| `レビュー待ち` | 実装が終わり、利用者のレビューを待っている |
| `確認中` | レビューを通過し、チェックリストの確認を進めている |
| `完了` | 確認が終わった |

## 進め方

1. 案件フォルダを作り、下のテンプレートで `README.md` を書く。状態は `文書作成` にする。
2. 仕様を変えるときは、`docs/spec.md`（データの作り方なら `docs/content-guide.md`）を先に更新する。
3. 状態を `着手` にして実装する。
4. 実装が終わったら、状態を `レビュー待ち` にする。開発サーバを起動したまま、利用者に画面を動かして見てもらう。直す点が出たら直して、もう一度レビューを受ける。
5. 利用者から問題なしと言われたら、状態を `確認中` にし、チェックリストを開発サーバで確かめる。
6. すべての項目が `確認済み` になったら、状態を `完了` にする。

## 確認のチェックリスト

画面の確認は、狭い幅（幅 390px 前後）と広い幅（幅 1280px 前後）の両方で行う。

```json
{
  "title": "〇〇 実装後の確認",
  "items": [
    {
      "id": 1,
      "viewport": "狭い幅",
      "text": "確かめる内容",
      "status": "未着手",
      "comments": []
    }
  ]
}
```

- 状態は `未着手`、`要見直し`、`確認済み` である。
- `comments` の要素は `role`（`確認`）と `text` である。コメントは追記し、過去の文は消さない。
- `確認済み` にするときは、画面で見た結果（見た回と問番号、測った値）を `text` に書く。状態だけを変えて、コメントを空のままにしない。
- `要見直し` にするときは、満たさなかった点を書く。直したら確かめ直し、結果を新しいコメントとして足してから `確認済み` にする。

## テンプレート

```markdown
---
status: 文書作成
---

# 案件の名前

## 目的

## 決めたこと

## 今回含めないもの

## 触るファイル

| パス | 内容 |
| --- | --- |

## 手順

## 確認

`checklist.json` で確かめる。
```
