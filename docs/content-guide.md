# 問題データの作り方

午前Ⅱの問題データ（`public/data/<id>.json`）を作るときの恒久的な手順と観点である。回を追加するとき、問題文や解説を直すときは、この文書に従う。進捗は、その作業の案件フォルダ（`docs/changes/NNNN-*/`）に置く。

## 流れ

1回分は次の順に作る。前の段階がその回のすべての問で終わってから、次の段階に入る。

1. **取得**: `scripts/fetch_exams.py` で、問題冊子と解答例を `exams/<id>/` に置く。元の URL は `exams/manifest.json` に残る。
2. **切り出しと正解**: `scripts/build_exam.py <id>` で、問題画像と、`no`・`answer`・`image` だけの回の JSON を作る。正解は解答例 PDF のテキストから取る。
3. **問題文**: 問題画像から `stem`、`choices`、`visuals` を起こし、レビューを受ける。
4. **解説**: `explanation` を書き、レビューを受ける。
5. **検証**: `uv run scripts/validate_data.py` が通ることを確かめる。

作る人とレビューする人は分ける。レビューはサブエージェントに任せる（後述の「レビューの進め方」）。

## 問題文

問題冊子はページ全体が画像なので、問題画像から読み取って起こす。

| 項目 | 内容 |
| --- | --- |
| `stem` | 設問文。表がある問は、表の中身も Markdown の表でここに書く |
| `choices` | ア、イ、ウ、エの本文。肢が表のときは、その表も Markdown の表で書く |
| `visuals` | `figure`（図・グラフ）、`table`（表）、`image`（図でも表でもない画像）。複数同時にあってよい。該当がなければ空配列 |

- 図そのものは文字にしない。`visuals` に `figure` を入れる。
- 表は Markdown の表にして `stem` または `choices` に含め、`visuals` に `table` を入れる。セルの結合や、一つのセルの中の複数行は、結合している範囲を文で補う。
- 句読点と用語の文字は画像に合わせる（IPA の冊子は「，」と「．」を使う）。折り返しの改行は、文のつながりが分かる形に詰めてよい。
- `no`、`answer`、`image` は変えない。

### 問題文のレビューの観点

1. `stem` が、図と表以外の設問文と一致する。
2. `choices` のア〜エが、画像の各肢と一致する。肢の取り違えがない。
3. 表は Markdown の表として `stem` または `choices` に含まれ、`visuals` に `table` がある。セルの結合などは文で補われている。
4. 図・グラフは文字にされず、`visuals` に `figure` がある。図でも表でもない画像は `image` である。該当がなければ `visuals` は空配列である。
5. `no`、`answer`、`image` が変わっていない。

## 解説

公式資料に解説はない。正解と矛盾しない文章を書き、`explanation` に保存する。一つの `explanation` に、ア〜エの4肢についての文を入れる。

### 解説の観点

1. 問題文の言い換えだけで終わらせない。用語の意味、仕組み、背景、具体例のうち、正誤の理由に必要なものを書く。問題文に書いてあることや、問題文から容易に想像できる説明は繰り返さない。問題文と関係のない事項は書かない。
2. 各肢に対応する一般的な用語、手法、契約形態、規格、理論があれば、それを特定して特徴や仕組みを書く。肢の本文が用語の名前だけのときは、その意味を短く書く。複数の誤りの肢が同じ点で食い違うときも、それぞれの意味は書く。意味が問題文やその肢の本文にすでに書いてあるときは、名前を特定するだけで繰り返さない。
3. 肢全体に対応する一般的な概念がなければ、その旨を書く。記述の一部が既存の概念に似ているときは、類似点と相違点を書く。
4. 誤りの肢は、どの記述が、どの概念のどの特徴と食い違うかを書く。必要なときは短い事例や数値を使う。
5. 計算問題で、問う値が一つに定まるときは、正解の計算だけを書く。誤答の解説は書かない。最も大きくなるもの、または最も小さくなるものを選ぶ問は、各肢の結果を書くか、式にして最大または最小を求める。誤りの肢には、その計算結果以外の解説は書かない。
6. 用語、制度、契約の説明が正確かを確かめる。似た概念を混同しない。一般的な傾向を、例外のない規則として書かない。法令や契約条件で扱いが分かれるときは、その違いを踏まえる。根拠を確認できないときは断定しない。
7. 長さは、正解の根拠、誤りの理由、用語の理解に必要な情報に絞る。目安は全体で 150〜300 字である。肢が名前だけで意味の説明が要るとき、各肢の計算結果を比べるときは、超えてよい。
8. 解説は、その問の `answer` と一致する。

### 出題時と現在とで基準が違う問

PM の午前Ⅱは、PMBOK ガイド、JIS Q 21500 / ISO 21500、民法、下請法、労働者派遣法などに基づく問が多い。これらは改版・改正されている。

- 正解は IPA の解答例のままとする。変えない。
- 出題当時の基準で書かれた問は、解説はまず当時の基準で正解を説明する。そのうえで、現在の基準で扱いが変わっているときは、その点を1文で添える（例: 「PMBOK ガイド第7版では、知識エリアではなくパフォーマンス領域で整理している。」「2020年4月の民法改正で、瑕疵担保責任は契約不適合責任に改められた。」）。
- 改版・改正の内容は、確かめられたものだけを書く。確かめられないときは書かない。

### 見本

次は、参照元（システムアーキテクト試験の演習）で観点の見本にした解説である。肢がすでに中身を書いている箇所（ウ）は名前だけにし、名前だけでは足りない箇所は意味を書いている。文をそのまま流用しない。

> ラボ契約は、一定以上の発注を約束する代わりに、スキルや人数の基準を満たす要員をベンダーが確保する契約である。イが正解である。アの「担当者の指名」と「直接の指揮命令」を両立する契約形態は、一般的なものでは見当たらない。紹介予定派遣は該当するが、あまり一般的ではない。ウはレベニューシェアの説明である。エは実稼働だけの精算で、通常一定以上の発注が前提となるラボ契約には一致しない。

## チェックリスト

進捗は、作業の案件フォルダの `checklist/<id>.json` に回ごとに置く。`public/data/` には置かない。状態とコメントをサイトに出さないためである。

```json
{
  "examId": "2025-r07-aki",
  "title": "令和7年度秋期",
  "stems": [
    { "no": 1, "status": "未着手", "comments": [] }
  ],
  "explanations": [
    { "no": 1, "choice": "ア", "status": "未着手", "comments": [] }
  ]
}
```

- `stems` は問ごとに25行、`explanations` は肢ごとに100行である。正解の肢は問題 JSON の `answer` で分かるので、チェックリストには複製しない。
- `comments` の要素は `role`（`作成` または `レビュー`）と `text` である。コメントは追記し、過去の文は消さない。
- 起こした本文や解説はチェックリストに複製しない。

状態は次のとおり。

| 状態 | 意味 |
| --- | --- |
| `未着手` | まだ作っていない |
| `作成済み` | 作成側が問題 JSON に入れ終わり、レビュー待ち |
| `要見直し` | レビューが観点を満たさないと判断した |
| `確認済み` | レビューが観点を満たすと判断した |

## レビューの進め方

1. 作成側は、その回の行を `作成済み` にし、コメントに判断に迷った点を書く（問題文では図・表の判断や読みにくい文字、解説では足した用語や断定を避けた点）。
2. レビューは、作成時の会話を持たないサブエージェントに頼む。渡すのは、この文書、問題 JSON、問題画像、チェックリストのパスだけである。作成側の考えを口頭で補わない。
3. レビュー側は、`作成済み` の行だけを見る。問題文は画像と照らし、解説は問題文・問題画像と照らす。観点を満たす行は `確認済み` にし、満たさない行は `要見直し` にして、コメントに観点の番号と理由を書く。レビュー側は問題 JSON を直さない。
4. 作成側は `要見直し` の行だけを直し、`作成済み` に戻す。解説で、ほかの肢の文まで変えたときは、その肢も `作成済み` に戻す。
5. その回の行がすべて `確認済み` になるまで、2〜4を繰り返す。

問題文の行がすべて `確認済み` になるまで、その回の解説には入らない。
